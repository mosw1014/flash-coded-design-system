A bold, direct, energetic brand.

This design system turns the Flash brand into reusable building blocks. Before the tokens and components, here's a quick acquaintance with what makes Flash look and feel like Flash.

Brand essence
Three words guide every Flash surface. When in doubt, choose the option that is bolder, clearer, and more energetic.
Bold
Confident and unafraid. Big type, strong contrast, one clear focal point per surface.
Direct
Plain, confident English. No hype, no filler — say the thing and move on.
Energetic
Alive and electric. Flash Green is the spark — used sparingly so it always lands.
Core colours
The Flash palette is built on three colours. Green is the brand, but it's emphasis — not a default. Black and white do most of the work; green marks the single most important thing.

Typography
Two typefaces, clearly divided. Never swap their roles.
Aa
Satoshi
The workhorse. All app UI, body copy, labels, and most headlines. A variable font spanning Light to Black.
AA

Display only. Short, punchy marketing headlines — loud, wide, uppercase. Never body copy.
The logo
A bull silhouette in a green circle, paired with the lowercase flash wordmark. The variant changes with the background so the mark always has contrast.
On black
On Flash Green — black mark
On white — green icon
Never recreate the logo. Always use the supplied SVG files, keep clear space around it, and use one logo per layout.
Working principles
A handful of rules keep every Flash surface consistent.
  • 1
    Green is the spark. Reserve it for the single most important element. Everything else is black or white.
  • 2
    Hierarchy through size and weight — never grey or reduced opacity. Same level, same style.
  • 3
    Generous, rounded shapes. 30px radius on cards and containers, fully rounded pills and buttons.
  • 4
    Plain, confident words. Direct and energetic — say the thing without hype.

When to use
Icons speed up scanning when they’re unambiguous. When in doubt, pair one with a text label.
✓ Do
  • Keep every icon on the same 24px grid and 1.8px stroke — never mix weights.
  • Recolour and resize with color and --icn-size, not by editing the SVG.

✗ Don’t
  • Don’t mix filled and outline styles in the same view.
  • Don’t use an icon alone for a critical, unfamiliar action.
  • Don’t hardcode a fill colour on an icon — it breaks dark mode.

Checkboxes & Radios v1.0.0

Selection controls built on real native inputs, styled with the brand green. 2 control types · 3 sizes · 5 states · light & dark mode. Checkboxes for independent on/off choices; radios for one-of-many.

Quick copy
Grab a ready-made instance. Every control here is a real, focusable native input.
Quick copy
Use these instances if you’re here to quickly grab a copy.
Labels & tap target
Always wrap the control and its text in a single <label> so the whole row is clickable. Keep the interactive row at least 44×44px for comfortable touch targets.
When to use which
Checkboxes and radios look similar but answer different questions.
✓ Do
  • Use a checkbox for independent on/off options, or a single opt-in (terms, marketing).
  • Use radios when exactly one option from a set must be chosen and all options are worth showing.
  • Give every control a visible, clickable text label.
  • Pre-select a sensible default for radio groups.
✗ Don’t
  • Don’t use radios for a yes/no toggle — use a single checkbox or a switch.
  • Don’t use checkboxes when only one choice is allowed.
  • Don’t leave a radio group with no option selected once the user has interacted.
  • Don’t nest more than one level of dependent checkboxes.

Tags & Badges v1.0.0

Static labelling: tags for categorising, count badges for notifications, avatar badges for identity, and status dots for state · 5 tag variants · light & dark mode · interactive tag playground.

Tag or Chip?
Both are small pills of text — the difference is emphasis and interactivity. Reach for a tag to quietly categorise; reach for a Chip when the element is selectable, removable, or needs to shout.
✓ Do
  • Use a tag for read-only metadata — a transaction type, an API version, a category like “Betting”.
  • Use a count badge for unread or pending totals, and its dot-only form when the exact number doesn’t matter.
  • Use a status dot inline with a label to show live state — Active, Degraded, Offline.
  • Keep tag colour meaningful — lean on Neutral unless a semantic colour genuinely adds signal.
✗ Don’t
  • Don’t make a tag clickable or removable — that’s a chip’s job.
  • Don’t stack more than a couple of tags on one row — they stop reading as metadata and start looking like filters.
  • Don’t show a count badge with “0” — hide it, or drop to a dot.
  • Don’t rely on dot colour alone for critical status — pair it with a text label.

Bottom Sheets v1.0.1

A drawer-style sheet that slides up from the bottom of the screen, built from the SheetHeader block (with or without a back arrow, compact or full screen) plus a body and a footer button group. Flash brand only · interactive playground included.

When to use which
Bottom sheets and dialogs both interrupt the current screen to ask for input or show detail — the right choice depends on how much room the content needs and how attached it is to the page underneath.
✓ Do
  • Use a compact sheet for a short, focused task — confirming an action, picking from a short list, showing a summary.
  • Use full screen when the content needs the whole viewport — a multi-field form, a long list, or a flow with its own steps.
  • Add the back arrow only when the sheet is one step in a flow the person can step back out of.
  • Keep the footer to one primary action, with a secondary action alongside it where needed.
✗ Don’t
  • Don’t use a bottom sheet for a simple yes/no confirmation — a dialog is quicker to dismiss and keeps context visible.
  • Don’t add a back arrow on the first step of a flow — there’s nowhere for it to go.
  • Don’t drop the drag handle on a full screen sheet — it’s still dismissible by swipe, so the affordance should stay.
  • Don’t bury the primary action below the fold on a full screen sheet — keep the footer pinned.

Tabs v1.2.0

A horizontal tab bar for switching between views within a single screen. Built from a Tab item (with or without a leading icon, in Regular or Small) composed into a Tabs list that shares one bottom divider. The active tab is marked by a weighted label and an inverse underline. Adapts to light & dark via semantic tokens.

Interactive
A working Tabs list — click any tab to switch the panel below. Only one tab is active at a time; the underline slides to the selected item.
Sizes
Regular (56px tall, 16px label) is the default for primary, page-level navigation. Small (46px tall, 13px label) suits denser or secondary contexts such as inside a card or panel.
With & without icon
A tab item can carry an optional leading icon in a rounded neutral chip. Use icons only when they add scanning value — keep every tab in a list consistent, either all with icons or all without.

Dropdown v1.2.0

A labelled select trigger that opens a card of options, in single-select (one exclusive choice, a plain label with a trailing check) or multi-select (several independent checkboxes) form. Built from a Dropdown field (label, trigger button, assistive caption) in Bordered or Rounded style, Medium or Small size, paired with a Dropdown list item inside the options card, plus an optional search input.

Single-select
A working dropdown — click the trigger to open the list, click an option to select it and close. Click outside or press Esc to dismiss without changing the selection.
Multi-select
Click as many options as needed — each checkbox toggles independently and the menu stays open. The trigger summarises the pick as a label, or “N selected” once there’s more than one. Use Clear to reset, or Done to close.
Style
Bordered shows a visible grey outline at rest — use it wherever it needs to read clearly as a form field. Rounded hides the outline until hover/focus/open, for a softer, pill-shaped trigger that suits denser filter bars.
Sizes
Medium (48px trigger) is the default for standalone forms. Small (40px trigger) suits denser contexts such as filter rows or table toolbars.
Placeholder & selected
With no option chosen, the trigger shows a subtle placeholder in Body m – semibold / text-subtle. Once an option is selected, the same slot switches to text-primary and keeps the selected item highlighted in the list.
States
Every trigger resolves to one of four states. Default sits on a muted fill; Hover darkens the fill slightly; Keyboard focus and Open both switch the border to the inverse colour, and Open additionally flips the chevron and reveals the options card.
Options list & search
Each row is a Dropdown list item — hover-highlighted, with the active choice on a success tint. Single-select shows a trailing check mark; multi-select (above) shows a real checkbox, since more than one row can be active. The card can optionally lead with a search input to filter long option lists.

When to use
Dropdowns pick one value from a bounded list without leaving the current screen — they are not a substitute for navigation, and not the right tool for open-ended text entry.
✓ Do
  • Use a dropdown when there are roughly 5–15 known options.
  • Reach for multi-select only when picking several values genuinely makes sense — otherwise use single-select.
  • Always show a clear placeholder until a value is chosen — never default to a hidden first option.
  • Add the search input once a list runs past a screen’s worth of items.
  • Pair the trigger with a label and, where useful, an assistive caption explaining the choice.
✗ Don’t
  • Don’t use a dropdown for 2–3 options — radios or a segmented control are faster to scan and select.
  • Don’t use multi-select when only one answer is ever valid — that’s just extra clicks.
  • Don’t close a multi-select menu the instant one box is ticked — let the user finish, then confirm with Done.
  • Don’t bury a primary, frequently-changed filter three menus deep — surface it directly.
  • Don’t mix Bordered and Rounded styles within the same form.
  • Don’t rely on the placeholder colour alone to signal “required” — pair it with real validation.

A small floating label that explains an element on hover or keyboard focus. Pure CSS — it appears on :hover and :focus-within, so keyboard users get it too. Reserve it for short, non-essential hints.

When to use
Tooltips are supplementary. If the user must read it to succeed, put it on the page instead.
✓ Do
  • Label icon-only buttons and clarify terse controls.
  • Keep the text to a short phrase — a line or two at most.
  • Make triggers focusable so keyboard users can reveal them.
✗ Don’t
  • Don’t hide essential information or actions inside a tooltip.
  • Don’t put links, buttons or long copy in one — use a popover.
  • Don’t depend on hover alone on touch devices, where it never fires.

Accordion v1.0.0

Stacked headers that expand to reveal content, for progressively disclosing long or secondary information. Built on native <details> elements, so expand/collapse works without JavaScript and stays accessible.

Single open
Grouped with a shared name, so opening one item closes the others — ideal for FAQs where one answer at a time keeps things tidy.

Yes — full or partial refunds can be issued from a transaction’s detail view for up to 180 days after the sale.
Which cards are supported?›
All major schemes are accepted, including Visa, Mastercard and domestic debit networks.
Multiple open
Without a shared name, items open independently, so several can be expanded at once. Use this when sections are unrelated.
Business details›
Legal entity name, registration number and trading address.
Bank account›
The account where settled funds are deposited.
When to use
Accordions trade visibility for density. Only fold away content the user won’t always need.
✓ Do
  • Use for FAQs, optional settings and long secondary content.
  • Write headers that describe exactly what’s inside.
  • Default the most useful item open when it helps.
✗ Don’t
  • Don’t bury content users need on every visit.
  • Don’t nest accordions inside accordions.
  • Don’t use one for a single item — just show it.

Skeleton v1.0.0

A shimmering placeholder that mirrors content’s shape while it loads, so the layout doesn’t jump when data arrives. Built from neutral surface tokens and honours prefers-reduced-motion.

Building blocks
Compose skeletons from three primitives — lines, blocks and circles — sized to match the real content they stand in for.
Text lines
Circle
Block
Composed
Real-world groupings: a media row (avatar + two lines) and a content card. Match the skeleton to the component it replaces.
When to use
Skeletons work best when you know the shape of what’s coming and the wait is more than a moment.
✓ Do
  • Mirror the final layout so content doesn’t shift on load.
  • Use for lists, tables and cards fetched from the network.
  • Keep the shimmer subtle and stop it for reduced-motion users.
✗ Don’t
  • Don’t use a skeleton for a sub-second load — it just flickers.
  • Don’t use one for a small indeterminate action — use a spinner.
  • Don’t let the placeholder differ wildly from the real content.
